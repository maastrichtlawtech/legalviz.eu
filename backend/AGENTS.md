# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Backend-only notes. The root [AGENTS.md](../AGENTS.md) has the monorepo picture and the cross-cutting **cache-version table** (bump these when you change cached output). [backend/README.md](README.md) documents every CLI command, API endpoint, MCP tool, and environment variable in full — read it before adding or changing routes/commands.

## Commands (run from `backend/`)

```bash
npm start                     # API server on :3000 (or $PORT)
npm run dev                   # API with --watch (auto-restart)
npm test                      # node --test search/*.test.js shared/*.test.js routes/*.test.js bin/*.test.js mcp/*.test.js
npm run test:search           # search tests only
npm run build:search-cache    # build the MiniSearch metadata cache into search/data/
npm run build:sqlite-data     # convert search + case-law JSON into the runtime SQLite store
npx eurlex <command>          # CLI (or `npm link` once, then `eurlex …`)
```

Single test file: `node --test search/search-ranking.test.js`.

The data store is loaded **once at server startup**, so restart the API after rebuilding it. Production prefers read-only `search/data/data.sqlite`; an explicit `DATA_SQLITE_PATH` is strict. JSON remains the local/fixture fallback. Until either source exists, `/api/search` returns `503 search_cache_unavailable`.

## What lives where

- **`shared/`** is imported by both the frontend and the CLI. The Formex parser (`shared/formex-parser/fmxParser.mjs`) runs in the browser, so keep it dependency-light and free of Node-only APIs; `shared/fmx-parser-node.js` is the Node wrapper. Fix parsing bugs here once — never fork them into `src/`.
  - Anything the parser imports must be **ESM with named exports**, since it reaches the browser (`src/utils/fmxParser.js` re-exports it). Vite's dev server serves these source files untransformed, so a CommonJS `module.exports` dependency is unresolvable in the browser — and `npm run build` will **not** catch it, because Rollup's commonjs plugin converts CJS at build time. That failure only appears in `npm run dev`, so exercise a law page there after touching the parser's imports. `shared/legal-reference-core.mjs` is the shared-with-CommonJS case: backend callers `require()` it through Node's require(esm) (hence `engines: >=22.12`), which is also why its exports stay named — a default export would reach them as `.default`.
- **AI services** — `recital-title-service.js`, `law-summary-service.js`, `article-digest-service.js`, `case-law-digest-service.js` — all follow one shape: clip source → hash → single-flight → **validate model output → then write cache** (never cache raw output). Zero-result digests are cached without an LLM call. The summary and two digest services share plumbing in `shared/ai-digest-utils.js` (text clipping, hashing, single-flight, cache read/write, citation grounding); `recital-title-service.js` predates it and keeps its own copy.
- **API-key resolution** is layered: feature-specific key → `OPENROUTER_API_KEY`. The `ARTICLE_QA_*` env vars are legacy fallbacks still wired into summaries/digests even though the Q&A prototype itself was removed (see [../docs/article-qa-plan.md](../docs/article-qa-plan.md)). The real ceiling on AI spend lives **outside this codebase**: the production OpenRouter account has a spend limit set in its dashboard. Don't remove or weaken it when rotating keys; when it's exhausted, AI endpoints fail on cache misses while cached results keep serving. In front of it the four generation routes carry their own guards, separate from the generic limiter: a per-IP generation budget that routes charge **only on a cache miss** (`req.chargeGeneration()`, `shared/rate-limit.js`), an origin allowlist (`shared/origin-guard.js` — CORS stays permissive for everything else), and a concurrency cap on outbound model calls inside `openrouter-chat.js`. Keep the charge-on-miss discipline when adding a generation route: charging in the middleware instead would bill readers for cache hits.
- **CJEU case-law parsing** (`shared/case-law-parser.js`, `shared/law-queries.js`) handles three historical shapes (post-2004 EUR-Lex Formex, pre-2004 OJ HTML, older Curia HTML) into structured `articleRefs`. Parsing and cache writes happen only offline; runtime is live SPARQL discovery plus read-only precomputed details. This is the most format-fragile code in the repo; changing its output shape means bumping `CASE_LAW_CACHE_FILE` (see the root cache table).

## Search-cache build & the raw-law corpus

`search/search-build.js` builds `data/search-cache.json`: harvest primary `reg|dir|dec` acts via SPARQL, then enrich each with an official title and an **excerpt** (recitals + Article 1/2 + definitions vocabulary, `buildExcerptFromCombined`). `build-sqlite-data.js` splits that asset into in-memory title/alias records plus a disk-backed FTS5 excerpt index and folds in precomputed case-law details. **Both** `findFmx4Uri`s — this one and the serving copy in `shared/fmx-service.js` — match on the `.<LANG>.fmx4` suffix alone, never on an allowlist of manifestation id formats. Cellar mints those ids from several production systems (`/oj/L_<9digits>`, `/oj/JOL_<year>_…_<NN>`, `/immc/planjo%3A<date>-<seq>`, `/celex/<CELEX>`, `/consolidation/…`), so enumerating them drops acts. Narrowing either copy fails **silently**: the search build under-harvests, and the serving path throws a 404 that `resolveParsedLaw` reads as "no Formex exists" and answers from the EUR-Lex HTML parser instead — a worse parse, no error. That drift is what left the CRR, the VAT Directive, MiFID II, PSD2 and Solvency II on the HTML path for years. `scripts/fmx-coverage-probe.mjs` re-checks it.

- **Raw-law corpus** (`search/law-corpus-store.js`): every fetched source is gzipped to `data/laws/<year>/<CELEX>.xml.gz` (FMX) or `data/laws-html/<year>/<CELEX>.html.gz` (EUR-Lex HTML). Enrichment is **corpus-first** — read the local copy, only hit the network on a miss — so re-runs, wider year ranges, and future parser fixes are **offline with no re-scraping**. The corpus is build-time only and **gitignored**. Derived JSON caches ship as release assets; Docker converts them into one `data.sqlite`, and production never parses the large JSON blobs at startup. The reverse-citation graph (`citation-graph.json.gz`, built by `search/citation-graph-build.js` over the same corpus) also ships as a release asset, but is gunzipped directly by `citation-graph-store.js` rather than folded into `data.sqlite` — add any new derived cache to the `DATA_RELEASE_TAG` release and the Dockerfile fetch loop rather than committing it.
- **Walk the corpus only through `search/corpus-files.js`.** The trees are `<year>/<CELEX>.<ext>.gz`, but not every file in them is an act: the corpus was seeded from a macOS checkout and carries an AppleDouble sidecar (`._<CELEX>.xml.gz`, Finder metadata rather than a gzip stream) beside each real file, which `tar` copies into every `corpus-vN` release. Filtering on extension alone counts them — `case-law-parse.js` fed 8,752 of them to gunzip on every pipeline run (`incorrect header check`), and the refresh-data scan derived ids like `._31953D0004` and handed 80,465 of them to the backfill. `listCorpusFiles` skips dotfiles; `refresh-corpus.yml` purges them on restore so new releases are clean. Readers that build a path from a CELEX id are unaffected — this is only about directory walks.
- **Metadata not in the corpus**: `date`, `eurovoc` and `inForce` are SPARQL metadata the on-disk source doesn't carry, so the offline rebuild can't reconstruct them. `date` is persisted at harvest time to `data/law-dates.json` (`law-corpus-dates.js`) and overlaid by `build-cache-from-corpus.js`; `eurovoc` comes from `search/eurovoc-enrich.js` and `inForce`/`endOfValidity` from `search/in-force-enrich.js`, both of which run as the **last step of both builders**, journaling to `data/eurovoc.json` / `data/in-force.json`. Those files are gitignored build-time artifacts; their contents ship **inside** the release asset (`date`/`eurovoc` from **`data-v6`**, `inForce` from **`data-v8`**) and `legal-cache-store.js` reads them straight off the record, merging nothing at startup. **Keep enrichment part of the build.** It is CELEX-keyed, so a pass bolted on afterwards gets generated against one cache and served alongside another — every record it never saw silently serves empty topics, and nothing errors. That is exactly how the `data-v5` corpus expansion left ~83% of records topic-less. It's best-effort (a Cellar outage ships the cache without the field rather than discarding a multi-hour harvest) and opt-out via `--no-eurovoc` / `--no-in-force`, which also restores a network-free corpus build — enrichment runs in the driver, and the parse workers keep their hard `fetch` block regardless. `search/fetch-eurovoc.js` and `search/fetch-in-force.js` backfill an existing cache without a rebuild; they are not the primary path.
- **`inForce` is a tri-state**: `true` / `false` / `null` = "Cellar has no status", which is ~13% of the corpus (it carries no in-force triple at all for most Commission Implementing Regulations). `false` means *not in force on the day Cellar was asked* and nothing more — there is **no repeal predicate** in Cellar, so a repealed act is indistinguishable from one that expired on its own terms, and it does not even separate those from an act **not yet** in force: acts are harvested when published, which is normally before entry into force, so a new act starts `false` and flips to `true` later. `false` is therefore not terminal, which is why `search/in-force-recheck.js` re-checks the whole cache rather than only the acts currently reading `true`. No UI may claim more than the flag says. The flag is authoritative: never derive status from dates (`32015L2366` is flagged in force with an `endOfValidity` already in the past). `9999-12-31` is a sentinel, normalised to `null`. `entry-into-force` **is** fetched, as `entryIntoForce`, and is what separates the two meanings of `false`: it is multi-valued (32026R1818 carries ten dates out to 2036), so `reduceBindings` takes the earliest — the date the act itself enters into force, the later ones staging individual provisions. Joining it costs ~1.19x extra rows per batch. `isNotYetInForce` in `search/legal-cache-store.js` and `lawStatus` in `src/utils/lawStatus.js` apply the same rule to ranking and to the UI; keep them in step.
- **Adding a field to the cache records? Two whitelists will silently eat it.** `enrichSearchRecord` spreads `{...record}`, so a new field flows through a JSON-backed dev checkout end to end — then vanishes in production, which loads from SQLite. `compactSqliteRecord` and the result mapping in `searchLaws()` (both in `legal-cache-store.js`) are hand-maintained field lists; nothing errors when one drops a field. The JSON/SQLite parity test in `legal-cache-store.test.js` guards this — add the field to its `publicRecord()` helper too. Pass fields through **unchanged** there (`inForce: enriched.inForce`, not `?? null`): `JSON.stringify` drops an undefined key, which is what keeps a record predating the field hydrating identically from both stores. Normalise at the wire boundary instead.
- **The corpus is English-only, and that bounds it far more than digitisation does.** Every stage filters to English (`FILTER(LANG(?title) = "en")`, `/EN/TXT/`, `ENG.fmx4`), so an act Cellar holds only in DAN/DEU/FRA/ITA/NLD — most pre-1973 acts, many pre-2004 — is permanently unindexable, not a harvest failure. A Cellar `manifestation_type` query that doesn't also filter `cdm:expression_uses_language <…/authority/language/ENG>` counts those as "missing" and overcounts wildly: issue #100 audited 942 supposedly-indexable gaps, of which **29** had any English rendition. Filter by language before concluding the corpus has a hole.
- **Whole acts missing (not a field)?** `search/backfill-cache.js --celex <ids|@file>` adds them to an existing cache (`.json` or `.json.gz`, so it patches the release asset in place), running the builder's steps in the builder's order. `reenrich-cache.js` is the opposite direction — it only refreshes records already present and can't create one.
- **FMX-less acts** (mostly pre-2000 — no Formex exists) are downloaded as raw HTML by `search/html-harvest.js`. It does **not** open pages in Chromium: `shared/eurlex-cookies.js` warms the WAF/Cloudflare cookies **once** with a headless browser, then all downloads go over plain `fetch` with those cookies (re-warm only on a 202 challenge). The parser for that HTML is `shared/eurlex-html-parser.js` (`parseStructuredHtmlToCombined`), which emits the same combined shape `buildExcerptFromCombined` consumes.
- Long unattended harvests: requests go through `requestWithRetry` (WAF 202 + 429/5xx + network backoff); the enrich process has a slow memory growth, so bulk runs recycle the node process every N records (`--maxRecords`) rather than run one long process.

## Gotchas

- SPARQL queries (`shared/law-queries.js`) take user-supplied CELEX ids and language codes — these are validated/escaped to prevent injection. Keep new queries parameterized; don't string-concat untrusted input.
- Rate limiting, cache eviction (`STORAGE_LIMIT_MB` / `HTML_CACHE_LIMIT_MB`), and timeouts are all env-configurable — see the Environment Variables table in the README before hard-coding limits.
